## 4. The JSON extension: `p_provider_fields.dropped_fields`

- **Optional.** An absent key leaves `card_attempt_finish` exactly as before: no extra check, event or flag.
- **Shape.** When the key is present its value is a JSON array of 0 to 17 elements; each element is a JSON object with
  exactly the two keys `field` and `rule`, both JSON strings, compared exactly (no trim, case folding or normalization):
  - `field` ∈ the 17 tokens finish already handles: `provider_reference`, `approval_number`, `voucher_number`,
    `deposit_id`, `card_last4`, `card_brand_code`, `pan_entry_mode`, `payment_method_code`, `approval_type`,
    `provider_status_code`, `provider_return_code`, `provider_saved_at`, `error_flag`, `phone_authorization`,
    `tip_amount`, `provider_amount`, `provider_currency`;
  - `rule` ∈ `charset`, `length`, `control_character`, `digit_run`, `masked_pattern`, `format`;
  - the seven non-text fields (`error_flag`, `phone_authorization`, `provider_return_code`, `provider_amount`,
    `tip_amount`, `provider_currency`, `provider_saved_at`) admit only `format`, the only rule their SQL field rule
    produces; the ten text fields admit all six.
- **Duplicates.** Within one call a field appears at most once: a second entry for the same field — identical or with
  another rule — is refused (the adapter emits one entry per field, so a repeat is a producer defect and fails closed).
  Across calls, identical `(field, rule)` evidence is deduplicated by the existing private-event index (one event per
  attempt, field and rule) and never aborts the later outcome; another rule for the same field in a later call is its
  own event, exactly as for a value failing SQL's own rule.
- **Contradiction.** A field named in `dropped_fields` must not also be a key of `p_provider_fields`, whatever its value
  (JSON `null` and an empty string included): a declared failure is never overridden by a surviving value.
- **Never carried.** No rejected value, free text, credential, vendor identifier, card data, source token or scope: the
  event's source is `p_source` and its organization, restaurant, branch, mode and device come from the addressed row.
- **Refusal.** A present key that is not such an array — any other JSON type (`null` included), more than 17 elements,
  a non-object element, a missing, extra or non-string key, an unknown token, an inapplicable rule, a repeated field or
  a contradicting key — RETURNS the existing typed refusal `{ok:false, error:'invalid_request', server_ts}` before the
  row lookup, any lock, any read of the attempt and any write (no event, ledger change, stamp, counter or audit), and the
  answer never echoes the supplied content. `invalid_request` is the existing answer for a malformed finish argument, so
  the answer contract gains no token.
- **Producer.** Only the adapter writes the key, from the `{field, rule}` tokens its reply reader computed (§6).
- **The 001D finish inputs.** The 001D packet §4.2 says that any key of `p_provider_fields` outside its table is
  ignored; **D-062** makes `dropped_fields` the one exception (that packet is frozen and is not edited).
- **Duplicate JSON keys.** PostgreSQL's `jsonb` keeps only the last of duplicate object keys when the argument is
  parsed, before the finish runs, so a discarded copy is never read or stored and the surviving value is validated as
  above; the adapter's serializer cannot emit a duplicate key (review SQL-6).

and every other routine, table, policy and grant stay as the 001D migration left them.

The body is the C2 body (CR-normalized `pg_get_functiondef` md5 `99040d865e5bcd17f66e40ffe5f956b0`, pinned by SA-135)
plus exactly three blocks, each opened by a comment line naming this Work ID and **D-062**:

- **Block A — declarations**, after the last existing declaration (`v_updated integer;`): the loop variables.

  (`select … for update`): the whole of §4, refusing with that same `invalid_request` answer. Each JSON-type test that

- **Block C — recording**, directly after the existing provider-field loop and before the M3 class step: for each entry

## 6. The adapter (producer)

- `lib/provider/engine.mjs`: for a 2xx provider reply that is a readable JSON object, the commit, lookup and release
  transports attach the failures that `extractReply` computed — exactly its `{field, rule}` tokens, one per failing
  allowlisted field (its text-policy, shape or format rule), in the profile's reply-key order — as `dropped_fields` to
  the classified fields, only when there is at least one; no field of a reply that is not a 2xx JSON object is
  extracted. The
  engine also exports `REPLY_KEY_TABLE`, the reply-key table as plain data, for the SQL parity test (review ADP-1). The classification functions are unchanged; with no failure the finish arguments are byte-identical to
  001E's. The failing value never leaves the extractor (rule G stands: it is never placed in an RPC argument).
- `handler.mjs`: the release finish passes the release result's fields instead of the fixed `{}`, so a release reply's
  evidence is recorded; a release result carries no provider value (`classifyRelease` returns none), so the release
  finish still records no reference, code or amount and its advisory semantics are unchanged.
- A TEST attempt never reads the card and provider-reference fields, so they never appear in `dropped_fields`.
- `index.ts` is unchanged: `providerProfile` stays `null`, so no provider call happens outside the tests (gate W1).
