1. PURPOSE AND STATUS

The cashier deliberately chooses a preparation duration while accepting a website Pickup request. A customer subsequently sees an approximate server-derived ready estimate. This is an informational acceptance estimate, not authority to mark an order ready, change preparation algorithms, create another order, send a print, or modify an existing decision.

This file proposes concrete wire/storage names and bounds for review. It is not an approved application contract, source implementation, migration, deployment, release approval or execution permit. 3. PROPOSED WIRE CONTRACT — REVIEW REQUIRED

Incoming authenticated acceptance:
  action: "accept"
  existing PIN/device/session/request/decision keys: unchanged
  preparation_minutes: integer JSON number, 1..240 inclusive [PROPOSED RANGE]

Quick choices: exactly 10,15,20,30,45,60. Custom entry is whole minutes within the reviewed bound. Reject strings, fractions, booleans, null, missing new-client selection, overflow and non-finite values. Reject action must not accept this extra key.

Legacy compatibility: absence of preparation_minutes keeps the existing old-client acceptance path and creates no ETA. New POS requires a deliberate valid choice; it never silently omits the field, defaults to a duration, or falls back to legacy acceptance if the new path is unavailable.

Proposed new named RPC:
  public/app.pos_accept_web_order_with_eta(
    p_pin_session_id uuid,
    p_device_id uuid,
    p_device_session_token text,
    p_request_id uuid,
    p_decision_id uuid,
    p_preparation_minutes integer)

Use a distinct explicit name, not an ambiguous PostgREST overload or default-argument change to the existing five-argument RPC. Edge routing selects this path only when the reviewed optional field exists and is valid. The old path remains supported. No per-restaurant/device UUID allowlist.

Proposed optional response field ONLY for a successfully NEGOTIATED v2 capability status read whose result is accepted. Legacy/no-header responses, existing SQL result/status functions, and submit responses never acquire this field:
  "acceptance_eta": {
    "preparation_minutes": 15,
    "accepted_at": "<UTC RFC3339 instant from winning decision decided_at>",
    "ready_at": "<UTC RFC3339 instant: accepted_at + 15 minutes>",
    "timezone": "<validated effective restaurant/branch IANA timezone>"
  }

The exact tuple is one atomic optional object. Its four fields are all required when present, with no unknown keys. The object must be absent for legacy/historical accepted requests and for pending, rejected and expired states. Do not emit null placeholders or partially populated estimates.

Validate integer bounds, parseable UTC instants, approved timezone, arithmetic consistency and accepted-only presence at producer and strict consumer boundaries. Canonicalize instants consistently without changing their meaning or manufacturing a new accepted timestamp. The customer whitelist must not expose internal order/employee/device IDs, decision fingerprints, PIN/session details or extra capabilities.

Existing safe error vocabulary can represent invalid_request, decision_conflict, request_expired and ordering_unavailable. Final error choice is part of reviewed implementation. Never expose raw SQL/HTTP/server exceptions; an error or timeout is not proof that acceptance did not commit.

3A. R2 PROPOSED RESPONSE-VERSION NEGOTIATION — NONAUTH, BACKEND FIRST

PROPOSED header name: X-BIZBOT-Order-Response-Version.
PROPOSED supported values: absent or the single string "1" means legacy; the single string "2" requests the new status representation. Names/values are NOT approved or implemented. HTTP-standard header-name case insensitivity is expected; comma-joined duplicates, unsupported/empty values and malformed values fail with a fixed invalid_request before any database RPC. Never log the raw header or use it as authorization.

This is an informational representation capability, not an employee, device, tenant, order, capability-token, notification or print credential. A caller who asks for version2 still needs the exact existing slug + UUIDv4 client_request_id + private canonical status_token. Missing/wrong/expired capability remains not_found; no estimate existence, private request ID, decision identity or table metadata may leak. Customer Authorization/apikey headers remain ignored for database authority; only the Edge's existing server-held service credential reaches service-only status RPCs. POS acceptance continues to use its independent real caller JWT/device/PIN guards.

For the first minimal slice, the new client attaches the proposed header ONLY to action=status. Submit bodies, requests and responses remain legacy and byte-compatible: no extra body key, order field, immutable request fingerprint, request ID, status token, idempotency identity, recovery record, URL or persisted setting. Header2 on action=submit is proposed to fail invalid_request before any write; absence/1 follows the unchanged submission path. This action restriction is also a review decision, not a deployed rule. Do not change or retry an uncertain submit to obtain ETA.

Explicit action/representation matrix:
- No header (including an already-open old customer tab), or supported legacy1, status: call existing get_web_order_request_status; apply the existing strict legacy projection; omit acceptance_eta ALWAYS, including orders accepted by new ETA-capable POS.
- Header2, status: call a NEW explicitly versioned, service-only capability status reader; apply a NEW strict v2 projection accepting only the complete optional accepted-only tuple. Error vocabulary/capability retention and private-data exclusions remain the existing contract.
- No header/legacy1, submit: call the existing selected live/test/pilot submit RPC exactly as today; use unchanged legacy projection; no ETA even for an accepted replay.
- Header2, submit in this first proposal: fixed pre-write invalid_request. New consumer never sends it for submit. No second submit, backend write retry or post-write status/enrichment query is hidden inside that path.

An accepted SUBMIT replay legitimately carries no ETA. A new consumer may perform one explicitly designed, bounded STATUS read with version2 after such an accepted result, retaining the same capability, to obtain the authoritative optional tuple. This is a read, not an acceptance/submission retry. Failure preserves the already-known accepted status, explains estimate unavailability if needed and never fabricates/restarts a timer. Absence in a legacy submit response must not be presented as proof that no sidecar exists. Review this read behavior with the controller recovery contract before implementation.

Keep existing app.web_order_public_result, app/public.get_web_order_request_status and all submit RPC definitions/shapes unchanged for this scope. In particular, do NOT globally append ETA to the shared old result helper: old submit-replay and status callers use it, including already-open strict tabs. Preserve their existing explicitly authorized rejection-reason projection without disclosing historical private reasons. No unconditional acceptance_eta field, null placeholder, body version key or generic allow-unknown-fields decoder anywhere.

A genuinely absent sidecar means the OPTIONAL key is absent. A present but inconsistent/corrupt tuple is an error/failed verification, not permission to guess, overwrite it, or quietly manufacture a legacy success. It passes its authorized scoped request row to the v2 result projection; neither a caller UUID alone nor a separately selected unbound row may reveal an estimate. 4. PROPOSED IMMUTABLE DATA AND ATOMICITY STRATEGY

Preferred candidate for review: new private append-only app.web_order_acceptance_estimates sidecar, keyed by the exact scoped winning request/decision. This avoids changing immutable request identity, existing legacy fingerprint semantics and historical decisions. Final schema names/constraints need security/database review.

Proposed columns:
- request_id: primary key and scoped foreign key to the accepted request/decision.
- organization_id, restaurant_id, branch_id, decision_id: exact tenant/winner binding.
- preparation_minutes: approved integer bound.
- accepted_at: copied exactly from winning web_order_decisions.decided_at.
- ready_at: server-derived accepted_at + duration, with an arithmetic CHECK.
- timezone: validated effective IANA timezone captured with the estimate.
- intent_fingerprint: canonical versioned SHA256 binding request/action/duration and exact scoped decision identity.

Table protection: FORCE RLS; no direct client/anon/authenticated/service_role CRUD; fixed-search-path trusted function access only; append-only update/delete/truncate guards; scoped foreign keys; no customer read except through the existing capability-validated projection. No historical backfill.

Mandatory transaction behavior:
1. Validate new duration/timezone before canonical side effects.
2. Reuse current device/PIN/tenant/session validation, containment/device/request lock order and winner checks. Recheck authority/deadlines after waiting. Do not invert locks by introducing a metadata-first lock.
3. Reuse the existing acceptance/canonical/print-lease authority exactly once; do not fork a parallel acceptance implementation.
4. Insert metadata in the SAME SQL transaction as the winning acceptance. Read accepted_at from that winning decision, not from the caller or a later clock sample.
5. If metadata cannot be bound/inserted/verified after a new acceptance, roll back ALL canonical/decision/lease effects. Returning an error JSON after the old accept succeeds would be unsafe if its writes could remain committed.
6. A wrapper can reuse existing acceptance only after its enclosing exception/subtransaction structure proves full rollback. If that proof cannot be made, revise the design before code; do not weaken atomicity.
7. Preserve legacy web_order_decisions.payload_hash and protected request trigger. Sidecar binding does not permit retroactive attachment to an already accepted legacy request.

Required outcomes:
- Old client accepts: existing result, no estimate.
- New decision commits with duration: one order, one original print authority and one immutable estimate.
- Same exact winning intent and duration: replay original accepted_at/ready_at/timezone; no timestamp reset, insert or new lease.
- Same decision identity but changed duration: decision_conflict.
- Accepted legacy request with no estimate: new ETA attempt conflicts; no invented/backfilled estimate.
- Another device/PIN/decision after acceptance: existing winner conflict; cannot edit ETA or create print permission.
- Concurrent accepts or accept/reject: one existing canonical winner only; loser writes no estimate.
- Rejected/expired: no estimate.

5. TIME AND DISPLAY AUTHORITY

accepted_at is the winning final decision timestamp sampled by PostgreSQL clock_timestamp after canonical work and before COMMIT; it is NOT a precise commit timestamp. ready_at is an absolute instant computed once from that unchanged decision value. expires_at remains the PENDING deadline and is never reused as ETA.

Proposed timezone authority: effective branch timezone, otherwise restaurant timezone, following existing public storefront rules. Capture that validated IANA value with the estimate. A missing/invalid zone denies only the new ETA path before acceptance; do not silently substitute browser/Android/POS zone. Old no-estimate acceptance remains compatible. This behavior needs explicit contract review.

Customer UI presents localized approximate duration and/or approximate ready time in AR/HE/EN, with a date when crossing the restaurant's local day. Recommended first slice omits a live countdown: absolute estimate plus duration avoids new device-clock authority. If a countdown is required later, define its clock contract first.

For an ETA-aware negotiated status consumer, refreshing, resuming, reopening or changing language fetches the original tuple through the existing status capability; it cannot restart the duration. Same-intent replay returns the stored timezone even if current restaurant settings later change; only a genuinely NEW pending acceptance resolves/validates the current effective timezone. An elapsed estimate changes informational copy only: never state='ready', autoaccept, cancellation authority, dispatch, reprint or any other business transition.
